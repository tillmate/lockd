# Architecture decisions

## ADR 001 — New local app, PostgreSQL first

No repository or integrations existed; the owner confirmed this. Use the recommended Next.js/TypeScript family. Supabase credentials and a project were not supplied, and creating production infrastructure is excluded. Native embedded-postgres starts a real PostgreSQL 18 server with disk persistence and independent TCP connections. SQL migrations are portable to managed PostgreSQL. The local launcher is a developer tool, not a production database supervisor.

Supabase Auth/Storage adoption, if selected later, requires a deliberate identity and storage migration, not changing environment variables and assuming compatibility. Existing tokens, agreement history and receipt access must remain intact.

## ADR 002 — Transaction boundaries and roles

Runtime database credentials belong only to the Next.js server. They are not Supabase browser credentials. The server places hashes of authenticated session/guest cookies in transaction-local settings. RLS resolves those hashes against database sessions/bookings; no client-provided tenant ID establishes authority.

Functions have a fixed `lockd,pg_temp` search path. Auth functions are callable only by the trusted backend runtime; table reads for auth records are not granted. All business mutations are via functions; raw UPDATE/INSERT/DELETE grants are absent. The migration owner deliberately has higher authority and must never be used by web routes.

Each booking mutation locks the DJ account first, then the booking. Both Free-cap allocation and occupancy insertion happen in that transaction. All holds, confirmed bookings and personal blocks share `occupied_slots`; its database exclusion constraint is the last collision guard. Expired provisional occupancy is removed before new allocation. The worker improves notification timeliness; integrity does not depend on its uptime.

## ADR 003 — Exact hold policy

Original expiry is persisted as creation +48 hours. Validated evidence accepted before that expiry sets `grace_used=true` and expiry to original +24 hours. Never add 24 hours to the upload time. Subsequent proof is allowed during grace but cannot extend it. An expired booking can retain new evidence and actual-funds verification; its status remains expired and its slot stays released.

Timing is determined by the database after obtaining the account lock. A request arriving at an HTTP handler is not considered accepted proof until its image has validated and its transaction can accept the claim. This deliberately errs against reviving an expired hold. A request started earlier but blocked by another transaction must not bypass expiry.

For this slice, online events must start more than 72 hours and no more than 730 days ahead. This avoids a hold/grace outliving the performance. This is a documented engineering restriction, not a founder-approved new pricing or cancellation rule. Short-notice requests need a separately designed expedited workflow.

## ADR 004 — Evidence and verification

PNG/JPEG only, up to 5 MB and 20 million decoded pixels. Re-encode to PNG without metadata. Save the private bytes and claim in the same database transaction. This avoids public buckets and storage/database rollback mismatches. It trades database size for simpler privacy and atomicity; object storage and retention jobs are a later operational requirement.

Image digest uniqueness is per DJ. An exact retry with the same booking, reference and amount returns the prior claim. Reusing it with different claim details is rejected. This is exact duplicate detection, not forensic fraud detection. Verified bank references are unique per DJ to prevent crediting the same reference twice.

Each claim receives one immutable reconciliation decision. A partial receipt records only the actual verified amount; a distinct top-up claim is required for the remainder. When total actual verified funds reach the deposit and a live occupied slot and signature exist, the booking can become confirmed. Late funds remain recorded and produce an exception event requiring a new date/hold or DJ-managed refund. Lockd never reverses external money.

## ADR 005 — Guest access and signatures

Browser-generated 256-bit random capability is supplied with an idempotent hold request. It is sent over the local origin (HTTPS required for a future remote deployment), stored only as a hash in the database, and embedded in the private link fragment so it is absent from HTTP URL logs and referrers. The original capability must be retained by the client for link recovery; only the hash is persisted server-side.

The link is exchanged for an HttpOnly, SameSite=Strict cookie lasting one hour. Original link access expires 90 days after the event. A single browser guest cookie represents one open client booking at a time. Typed name plus explicit intent checkbox records agreement ID, exact content hash, identity supplied by the client and database timestamp. This records intent; it is not a claim of legal validation or independently verified client identity. IP/device collection is deferred pending privacy/legal review.

## ADR 006 — Development-only email and public source

> Delivery is superseded by ADR 011. The public-source guidance below still applies.

No customer communications are authorized or configured. A local mailbox makes verification/recovery testable without sending mail. Outbox notification events are stored transactionally; they are not falsely marked delivered. A production dispatcher needs an authorized provider, encrypted token delivery payloads, deduplication keys, retry scheduling and delivery audits. Do not repurpose the local mailbox as a public endpoint.

Public Git source was explicitly requested. Exclude `.local`, `.env.local`, database files, local mailbox tokens, traces and build caches. Screenshots included in `docs/evidence` contain only synthetic QA data. No production deployment is part of source publication.

## ADR 007 — Profile editing and immutable amendments

One package remains supported per DJ. Owner-only settings use an integer revision to reject stale writes, keep the shared slug stable, and append the previous private profile/package snapshot to an immutable audit table. Unpublishing stops new holds but leaves private bookings accessible. Existing price, terms, payment instructions, duration and occupied travel/setup buffers never change with profile edits.

An eligible confirmed booking can use one complimentary date change, requested at least 14 full days before the current event. Interpret “within 90 days” as within 90 days either side of the original event, still more than 72 hours in the future at proposal. Only a date change with unchanged venue/service/price is supported; new quotes and changed travel costs are separate future work. A proposal expires 48 hours after creation, an engineering limit independent of booking hold/grace.

Every proposal creates a new immutable agreement version referencing and preserving the current signed text and hash. Proposal alone is not consent. Both parties separately accept the exact new hash with typed names. Account then booking locks serialize signatures, cancellation and competing availability allocations. Original occupancy stays intact until the second acceptance atomically updates the existing occupied range. The proposed date is **not** reserved beforehand. The GiST exclusion constraint rechecks availability on application: a conflict rolls back the last signature and all changes, preserving the original slot. Original duration and buffers come from the booked occupied range, not the subsequently editable package.

Declines, withdrawals and expiry do not consume the complimentary move. History remains visible; only application increments the one-move counter and changes the active agreement version. Cancellation requests block proposal/acceptance until resolved; approved cancellation voids any pending amendment. Guest-link expiry extends to at least 90 days after a later event and never shortens unexpectedly. Expired proposal state is projected on reads and persisted when a replacement is proposed; no original reservation is released by amendment expiry.

## ADR 008 — Cancellation and non-custodial refund records

For an upcoming active booking, a client request records its database timestamp and reason without releasing occupancy. DJ review records approval or decline, the signed-contract/legal basis and explicit responsibility attestation. The proposed default refund suggestion uses request time: 50% of actual verified funds at >=14 full days, otherwise zero; half-cent rounding favors the client. This is a suggested contract default pending legal validation, not an automatically imposed legal conclusion. An owner may record a different client refund only with an explicit basis; all decisions retain suggested and decided amounts. DJ-initiated cancellation always requires 100% of actual verified funds. Refunds cannot exceed recorded verified funds.

Approval atomically marks cancellation, releases occupancy and preserves agreements/payment history. Refund obligation, DJ attestation of an already completed external transfer, and client acknowledgement of actual receipt are three distinct records. No provider is called or money transferred. A refund never subtracts from historical verified receipts or becomes Lockd revenue. A unique canonical transfer reference and immutable records prevent silent reuse or rewriting. One full refund attestation is supported; installment refunds, disputed/corrected decisions and expired-booking late-fund resolution need a separate audited workflow.

Use a **conservative deadline of seven calendar days** from approval for positive refunds, including client refunds. This is within seven business days without guessing a Jamaican holiday calendar. It is an explicit engineering commitment stricter than the DJ-cancellation maximum; legal/business approval remains a launch gate. The UI distinguishes an outstanding obligation from DJ-attested transfer and client-acknowledged receipt. Both parties receive durable outbox events, with no external delivery claimed.

## ADR 009 — Manual software invoices and paid access

Software billing uses separate invoice, claim, bank-reconciliation, grant and event tables. Exact server/database prices are J$3,500 monthly, J$36,000 annually and J$25,000 annually for eligible founders. The immutable invoice snapshots business billing identity and collection instructions. Only the owner or a freshly MFA-verified billing reviewer can read its private evidence; guest booking links have no billing authority. Existing image sanitation is reused. Receipt claims do not activate access. Independent staff attest actual business-bank receipt; immutable decisions, unique canonical bank references across all software invoices, and per-tenant locks prevent double credit. Rejected and partial receipts remain distinct from fully paid invoices.

The collection configuration defaults disabled. There is no HTTP endpoint to activate a live bank or grant a staff role. The local setup CLI is restricted to loopback, explicit local mode and synthetic `example.test` staff identities; its collection instructions expressly say not to send money and contain no account numbers. Live onboarding requires a separately approved bank/staff release process. Tax/business particulars and compliant invoice export remain launch dependencies; the HTML invoice does not claim tax compliance.

One outstanding invoice per account prevents conflicting unpaid renewals. An untouched unpaid invoice can be voided, preserving history. An invoice with claims or verified funds needs staff resolution instead. Renewals are requested explicitly in the final 15 days of a term or while overdue; there is no automatic charge or email. Same-plan early renewal preserves the original due date. Timely receipts extend from that date; late standard-plan payment starts a fresh term at reconciliation. Monthly/yearly calendar intervals use PostgreSQL UTC month/year arithmetic. Entitlement checks include seven calendar days after term end and use database wall-clock time inside hold allocation. Downgrade changes the new-hold cap without touching records or existing reservations. New paid access currently removes the three-active cap; other Pro product features are not fabricated.

Staff record the actual bank receipt time, at second precision. The bank timestamp, not proof-upload or reviewer time, controls founder renewal eligibility. A timely payment reviewed after grace can restore the founder rate, with access remaining Free until review. A genuinely late founding payment or fully paid invoice that loses the last cohort place becomes `requires_resolution`, preserves actual received funds and grants no replacement entitlement. A separate authorized alternative/refund process is required; this slice does not move or silently repurpose those funds.

Founding approval is independent of payment and does not reserve capacity. A global allocation lock is acquired after the tenant lock; unique permanent seats 1–50 are inserted only with approval and full actual payment. Seats never transfer or recycle, preserving “first 50.” The invoice request checks current capacity and warns that a pending invoice does not reserve a place. Concurrency tests fill 49 places, then reconcile two approved invoices simultaneously: one gets seat 50 and the other gets an explicit unapplied-funds exception. Billing totals show settled software invoice receipts separately from verified unapplied amounts; neither includes DJ event deposits or claims accounting revenue recognition.

## ADR 010 — Billing-only staff authority and MFA

Staff start with the existing verified email/password login, then enter a six-digit authenticator code. TOTP follows [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html): HMAC-SHA1, 30-second steps and at most one adjacent step of clock tolerance. Official SHA-1 test vectors include post-2038 times. Secrets are random 160-bit keys encrypted using AES-256-GCM with a separate 256-bit server environment key. They never appear in a browser response or public repository. Local enrollment is written only to an ignored private file for the developer to enroll; production enrollment/recovery is not implemented.

Successful codes consume a monotonically increasing counter under a row lock, preventing replay across sessions. An account-level database rate limit permits six attempts per five minutes. Step-up attaches to the existing hashed session for ten minutes; logout/reset cascades away the grant and disabling the role immediately denies access. Sensitive review functions recheck freshness after tenant-lock waits. MFA success, founding approval, reconciliation, invoice issuance/void and evidence submission have immutable audit events. Staff cannot reconcile their own invoice or approve their own founding eligibility.

The single role is restricted to software invoices, their proof images, totals and a minimal DJ eligibility projection. It does not bypass RLS for event agreements, client bookings or DJ deposit receipts. Scoped case support, moderation, privacy operations, phishing-resistant authentication, production staff provisioning and recovery remain separate work. The runtime server remains a trusted identity verifier (as with password login); database helper functions are not safe to expose directly to browser database clients.

## ADR 011 — Transactional email delivery (supersedes the delivery part of ADR 006)

The existing transactional outbox is now a delivery queue. Every business transition still writes its message row in the same database transaction as the state change, so a rolled-back booking never emails anyone and a committed one is never silently dropped. New rows cover the gaps found in the November 2026 takeover audit: client hold confirmation (with the private link), DJ booking request, agreement signed (both parties), and client link recovery. Existing event rows (evidence submitted, verification results, expiry, date changes, cancellations, refunds, billing events) are delivered as they were already queued. Rows queued before delivery existed were marked `suppressed` by the migration and are never sent.

**Roles.** A separate `lockd_notifier` login role can only execute four functions: claim a leased batch, read the rendering context of a row it currently leases, record an outcome and enqueue due reminders. It has no table grants and cannot call booking functions. The web runtime cannot read the queue or delivery history. The migration also closes a latent gap: 001's per-schema `ALTER DEFAULT PRIVILEGES … REVOKE` is a no-op in PostgreSQL, so functions added after 001 were PUBLIC-executable. 010 pins the runtime's exact existing function grants, revokes PUBLIC execution schema-wide and sets a global default so future functions need explicit grants.

**Secrets in links.** Verification, reset and client booking links are bearer tokens stored only as hashes. The web process encrypts the raw token with AES-256-GCM (`NOTIFICATION_KEY`, separate from the staff MFA key) and attaches it to the row it just created, in the same transaction, proving knowledge of the stored hash. The worker decrypts only at send time; the ciphertext is erased when the message is sent, fails or is suppressed (database CHECK). Verification and reset links that would already have expired are failed rather than sent.

**Delivery semantics.** Claims use `FOR UPDATE SKIP LOCKED` with a 120-second lease; only the current lease holder (matching attempt number with a live lease) can record an outcome. Retries back off 1 min → 5 min → 15 min → 1 h → 3 h → 6 h → 12 h; the eighth attempt is terminal. Provider validation errors fail immediately; auth, rate-limit, timeout and server errors retry so a configuration fix resumes delivery. The outbox id is the provider idempotency key, so a resend after a crash between provider acceptance and recording is deduplicated by the provider. Dedupe keys make enqueueing idempotent. Every attempt is an immutable `notification_attempts` row (provider, provider message id, outcome, error).

**Rendering.** Messages render at send time from a minimal database projection, so reminders whose condition no longer holds (agreement already signed, deposit verified, subscription renewed) are suppressed instead of sent. Verification outcomes use the totals recorded with the decision, not later top-ups. Emails carry no payment instructions, receipts or bank references; they link to the authorized page. User-entered names are HTML-escaped and stripped of control characters in subjects.

**Reminders** (worker, every five minutes, idempotent per deadline): unsigned agreement after 12 hours; deposit outstanding within 12 hours of hold expiry; DJ verification pending within 12 hours of expiry; DJ refund obligation within two days of its due date; Pro renewal due within seven days; payment not verified after term end (grace started); Pro lapsed to Free after the seven-day grace.

**Transports.** `EMAIL_PROVIDER=local` writes rendered messages to the ignored `.local/mailbox` and is refused outside explicit loopback local mode. `resend` posts to the Resend HTTPS API and requires an `https` `APP_ORIGIN`. `EMAIL_ALLOWED_DOMAINS` restricts staging delivery to listed recipient domains and audits everything else as suppressed. Unset means messages stay queued. The worker wakes on `LISTEN lockd_outbox` (statement trigger) and also polls every 15 seconds, and serves `GET /health` on loopback.

**Client link recovery.** Instead of rotating the single guest hash (which would let anyone who knows a booking id and client email lock the client out), recovery adds a row to `guest_links` and emails it to the address on the booking. The original link keeps working. Responses never reveal whether the address matched; at most ten extra links per booking, rate-limited per booking and per address.

Not yet implemented: provider bounce/complaint webhooks and recipient suppression lists, SMS/WhatsApp channels, per-user notification preferences, and staff tooling to inspect/requeue failed messages (next milestone).

## ADR 012 — Super Admin operations: scopes, listing moderation, delivery operations, audit

**Identity and step-up.** Staff keep the existing identity: a verified Lockd user enrolled in `billing_staff_members` with an encrypted TOTP secret. Membership retains its billing authority unchanged. Additional authority is a row per scope in `staff_scopes` (`listings`, `support`, `notifications`, `admin`; `admin` implies the operational scopes). `staff_can(scope)` requires the same ten-minute MFA step-up as billing. Every staff function checks it inside PostgreSQL and rechecks after waiting for a tenant lock; page guards are only presentation. The runtime has no grants on the new tables. Super Admins grant and revoke scopes for other enrolled staff with a recorded reason and can never change their own scopes. Enrolling new staff (TOTP secret) remains a reviewed provisioning process; `npm run staff:local` exists for synthetic local testing only.

**Listing moderation.** New accounts start `pending`: their own booking link works immediately (DJ-first self-service), but they are not shown in the public directory until a listings reviewer approves them. Staff can `restrict` a listing: the public page disappears and `create_hold` refuses new holds, while existing bookings, agreements, evidence and client links keep working so nobody loses records or access mid-dispute. Every decision is an immutable `listing_reviews` row with a reason code from a fixed list that must match the decision, plus a note; reviewers cannot review their own listing. The DJ receives an email and sees the restriction reason on the dashboard. Existing accounts were grandfathered as `approved`. Requiring approval before a booking link works at all is a one-line change if the owner prefers it; it was not chosen because it would block DJs from taking their first bookings.

**Notification operations.** Staff with `notifications` see delivery metadata for 30 days (kind, audience, masked recipient, attempts, provider, last error), never bodies, links or full addresses, and can requeue a failed message for one more attempt with a reason. Link emails (verification, reset, booking link) cannot be requeued because their encrypted token is erased on failure; the person requests a new link. Staff cannot requeue messages about their own account.

**Audit.** `staff_events` (append-only) records listing decisions, requeues and scope changes with reason code and note. The Super Admin audit view unifies these with billing staff events (MFA unlocks, founding approvals, reconciliations).

Not yet implemented: case-scoped support access to a specific booking's records, privacy/data-subject request workflow, incident log and feature flags, staff disable/recovery UI, and production staff enrollment.

## ADR 011/012 addendum — post-release review (migration 012)

An independent review of the email and Super Admin milestones found real defects; all were fixed in `db/012_review_hardening.sql` and the worker/templates, with regression tests:

- **Delivery semantics.** Leases are renewed per message when the worker starts on it (`notifier_context(id, attempt)`), so a slow batch never silently skips rows. `attempts` is only the lease generation; the 8-attempt budget counts recorded `notification_attempts`, so claims lost to a crash or shutdown never consume it. Graceful shutdown hands unstarted claims back (`notifier_release`). A decryption failure (missing or mismatched `NOTIFICATION_KEY`) is retried, keeping the encrypted link, and the worker refuses to start with delivery enabled but no key. Requeue no longer forges the attempt counter.
- **Message correctness.** Verification messages are classified by the DJ's decision: a rejection is always `proof_rejected` (with the reason), even on an expired hold or after a partial verification. Hold-phase messages (`hold_created`, `booking_request`, `agreement_signed`) are suppressed once the hold has ended. Deadline wording distinguishes the upload window from the final verification deadline after the one grace period. Cancellation wording no longer calls an unpaid hold "confirmed". The superseded "date change accepted" email is suppressed when the change applied. Evidence on an expired hold reaches the DJ as late evidence. Emails name the service from the signed agreement, not the editable package. Invoice notices also go to the invoice's billing email and quote the totals as of the event. The worker's database session runs in UTC like the runtime.
- **Locking and roles.** `outbox.account_id` lost its foreign key: the KEY SHARE lock it implied let the multi-account reminder job deadlock with `expire_all()`. The worker runs hold expiry under its own role, so the worker host needs no web-runtime credentials (which can mint sessions). Pool `error` handlers stop an idle-connection drop from crashing the worker or web server. `/health` returns 503 when a job has not succeeded recently or the outbox listener is down.
- **Staff authority.** Billing is now an explicit, revocable scope (existing billing staff were granted it); `admin` implies listings, support and notifications but never billing. Scope changes take a global advisory lock and re-check the actor's authority after it, so two admins cannot revoke each other into zero admins and a just-revoked admin's grant fails. Revocation works for disabled members. Requeue re-checks MFA after lock waits. The audit trail names who or what an action affected and excludes staff members' own DJ self-service billing. Staff authorization errors explain themselves in the UI, and a 403 re-renders the page so an expired step-up shows the authenticator prompt.
- **Forms.** Every submit button stays disabled until hydration, so a click on a slow connection can never natively submit a GET that puts a password or client details in the URL.

## ADR 013 — Case-scoped support access

Support staff need to help with disputes (payment discrepancies, cancellations and refunds, date changes, no-shows, fraud reports, account and delivery problems) without standing access to private booking data, and without impersonating anyone (no "log in as user").

**Case first, then records.** A staff member with the `support` scope and a fresh MFA step-up opens a case about one DJ account with a category, who raised it and a summary. Until a booking is linked, the case shows only candidate bookings' dates and statuses, never client details. Linking requires a written reason and is restricted by composite foreign keys to bookings of that case's DJ, so a case can never reach another tenant. Linked bookings' records (booking terms, agreement versions and signatures, payment claims with the DJ's decisions and bank references, date changes, cancellation, refund and acknowledgement records, booking history, and delivery metadata with masked addresses) are visible only while the case is open and its access window is live: 72 hours, extendable three times with a reason. Bearer secrets (guest link hashes, request hashes, encrypted link tokens) are never part of the projection.

**Evidence images** are fetched one at a time, only for a linked booking, with a written justification recorded with the view; the image is shown in the page and served `no-store`.

**Audit and immutability.** Opening, linking, every records view, every evidence view, notes, extensions and closure are `staff_events` rows; case links and notes are append-only, and a closed case is final (open a new case instead). Staff can never open or act on a case about their own account.

**Transparency.** The DJ receives an email when a case about their account is opened and closed, and sees open cases on their dashboard, except for fraud reports, where notice could prejudice the review. Client notification and client-raised case intake are handled out of band by support for now.

Deferred: two-person approval for evidence access, case assignment and hand-off, client-facing case notices, attachments, retention and deletion of case data (pending the owner's retention decision), and linking billing invoices to a case.
